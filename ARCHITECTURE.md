# КОКОС IV — архитектурный контракт и журнал источников

Этот документ фиксирует Gate A, метрический контракт сцены, правила построения и критерии QA для самостоятельного проекта `kokos-iv-smart-home`. Он не заменяет исходный дизайн-проект и не повышает достоверность реконструированных параметров. Единственный исполняемый владелец проектных данных — `src/data/project-manifest.js`; этот файл объясняет происхождение данных, ограничения и порядок их проверки.

Дата ревизии документа: 21 июля 2026 года.

## 1. Границы проекта и правила достоверности

Основной источник:

- `Дизайн-проект интерьера.pdf` (исходный клиентский альбом, не публикуется в репозитории);
- 60 физических страниц PDF;
- физический номер страницы PDF и номер листа внутри документа всегда указываются раздельно.

Дополнительные материалы:

Иерархия разрешения противоречий:

1. размерный архитектурный план;
2. разрезы, фасады и развёртки;
3. размерный план мебели;
4. планы потолков и освещения;
5. ведомости и спецификации;
6. интерьерные рендеры;
7. осторожная реконструкция по косвенным признакам.

Статусы достоверности:

| Статус | Значение |
|---|---|
| `confirmed` | Параметр читается в приоритетном листе либо однозначно связан с ним. |
| `provisional` | Параметр нужен для демонстрационной модели, но получен растровой оцифровкой, визуальной оценкой или неполным источником. |
| `proxy` | Реальные габарит, положение и ориентация сохранены, но форма предмета представлена аккуратным силуэтным заменителем. |

- отметка низа `sill = 0.150 м`;

Обязательные QA-кадры для каждого из семи объектов: из помещения, снаружи, под углом; каждый кадр в дневном и вечернем сценарии.

## 4. Решения пользователя и неподтверждённые параметры

20–21 июля 2026 года пользователь снял четыре блокирующие неоднозначности:

1. сгенерированный PNG 12,060×10,200 окончательно исключён из геометрии;
2. растровая оцифровка PDF разрешена при статусе `provisional`;
3. для provisional glazing разрешена отметка низа 0,150 м.
4. сгенерированный JPG освещения принят как подтверждение количества и относительной попомещенной раскладки светильников.

Поэтому моделирование продолжено без повышения достоверности этих параметров. Для перевода соответствующих сущностей в `confirmed` всё ещё нужны ответы:

1. Есть ли векторный PDF, DWG или полная наружная размерная цепь для подтверждения shell и абсолютных X/Z?
2. Какова правильная ширина остекления гардеробной: 1,775 м по обмеру или около 0,945 м по развёртке?
3. Есть ли ведомость окон/витражей с высотой, секциями, импостами, типом профиля, глухими/открывающимися створками и направлениями открывания?
4. Является ли `Hо = 3115` на листе 2 высотой самого проёма во всех семи случаях; есть ли отдельные отклонения по развёрткам?
5. Подтверждены ли чистовые потолочные отметки 3,405 / 3,305 / 3,265 м для всех помещений без локальных опусков?
6. Каковы точные конструкция, ткань, высота и положение карнизов четырёх моторизованных штор?
7. Нужны ли точные каталожные 3D-модели мебели и сантехники вместо текущих `proxy`, и доступны ли их артикулы/CAD?
8. Есть ли светотехнический расчёт или паспортные потоки/КСС для замены demo-интенсивностей?
9. Существует ли отдельный commissioning-манифест с реальными устройствами и разрешёнными интеграциями?

До получения этих данных остаются неподтверждёнными:

- конструктивные толщины стен;
- секционность, створки, профиль, tint и точные рамы всех семи витражей;
- точная форма, вертикальные размеры и артикула `proxy`-мебели;
- высота подвеса и фотометрия светильников;
- конструкция ниш и фактический отступ штор;
- цифровые цвета, roughness, transmission, IOR и другие runtime-параметры материалов;
- реальные климатические зоны и инженерные уставки;
- MQTT, KNX, Modbus, API или иные commissioning bindings.

## 5. Геометрический контракт

### 5.1 Система координат

| Параметр | Контракт |
|---|---|
| Единица | 1 единица Three.js = 1 метр. |
| Плоскость пола | X/Z. |
| Высота | Y. |
| Ноль пола | `Y = 0`. |
| Начало X/Z | Внутренний северо-западный угол мастер-спальни на листе 4. |
| Север | `−Z`. |
| Вращение | `rotationY` в радианах вокруг оси Y. |
| Позиция | `[X,Y,Z]`; для мебели Y — низ объекта. |
| Размер | `[sizeX,sizeY,sizeZ]`, всегда положительный. |
| Стена | Ось от `start[X,Z]` к `end[X,Z]`; `offset` проёма отсчитывается от `start`. |
| Масштаб | Всегда `1`; локальные произвольные масштабы комнат запрещены. |

Текущий внешний полигон shell:

```text
[-0.300,-0.300]
[ 6.785,-0.300]
[ 6.785,-0.200]
[17.980,-0.200]
[17.980, 7.405]
[ 9.460, 7.405]
[ 9.460,12.245]
[ 6.250,12.245]
[-0.300,12.245]
```

Этот полигон — **provisional растровая оцифровка**, а не повторный обмер. Его origin, envelope и уступы нельзя переносить в монтажную документацию.

### 5.2 Контракт сущности

Каждая пространственная сущность обязана иметь:

- стабильный глобально уникальный `id`;
- `roomId`, если сущность принадлежит помещению;
- положение и положительные размеры;
- `rotationY` для ориентированных объектов;
- `source.file`, `source.sheet`, `source.pdfPage`;
- `confidence` из `confirmed`, `provisional`, `proxy`;
- явные `allowedContacts` или точные `collisionParts`, если простой OBB недостаточен.

Manifest не импортирует React или Three.js. Сцена строится из manifest отдельными builder-функциями; новый объект должен подключаться заменой данных, а не переписыванием UI.

### 5.3 Инварианты проёмов и стекла

Порядок построения витража:

1. ось и толщина стены;
2. вычитание проёма по `offset`, `width`, `sill`, `height`;
3. одна рама внутри проёма;
4. одно отдельное стеклянное полотно;
5. штора только с внутренней стороны и с положительным зазором;
6. проверка изнутри, снаружи и под углом.

Недопустимы:

- стекло поверх сплошной стены;
- непрозрачная стена за проёмом;
- стекло и стена в одной плоскости;
- совпадающие стеклянные поверхности или двойные рамы;
- чёрное зеркальное стекло из-за ошибочной прозрачности/сортировки;
- придуманная секционность.

## 6. Gate B — manifest и автоматическая валидация

Владельцы:

- данные: `src/data/project-manifest.js`;
- структурная проверка: `src/scene/manifestValidator.js`;
- геометрические столкновения: `src/scene/collisionValidator.js`;
- CLI: `scripts/validate-manifest.mjs`;
- тесты валидатора: `tests/validator.test.mjs`.

Validator обязан проверять:

- глобальную уникальность ID, включая fixtures;
- метры, X/Z+Y и scale `1`;
- наличие и диапазон физических PDF-страниц у каждого источника;
- конечность координат, положительные размеры и корректные полигоны;
- самопересечения, наложения помещений и выход комнат за shell;
- ссылки на помещения, стены и материалы;
- положение проёмов внутри стены и отсутствие перекрывающихся проёмов;
- связи дверей, число полотен, петли и направление дуги;
- `sections = null`/`operable = null` как явное предупреждение для provisional glazing;
- принадлежность мебели помещению по ориентированным footprint/OBB;
- световые группы, fixtures, устройства и `visualId`;
- связь шторы с существующим проёмом и curtain-device;
- состояния `idle`, `pending`, `confirmed`, `error`, `offline`;
- площадь каждого помещения и сумму экспликации;
- коллизии и превышение разрешённой глубины контакта.

Численные defaults:

| Проверка | Значение |
|---|---:|
| Базовый epsilon | `1e-6` |
| Допуск площади комнаты | max(`0.05 м²`, `1%`) |
| Допуск общей площади | max(`0.10 м²`, `1%`) |
| Допуск касания | `0.002 м` |
| Максимальное разрешённое проникновение явно разрешённого контакта | `0.025 м` |
| Ошибка хорды дверной дуги | `0.002 м` |
| QA-размер collider светильника | fallback `0.060 м`; линейные символы используют собственный повёрнутый OBB по длине сегмента |
| QA-толщина стекла | `0.012 м` |
| QA-толщина шторы | `0.040 м` |

Gate B считается закрытым только при нуле ошибок и нуле неразрешённых коллизий. Предупреждения допустимы лишь как явная фиксация происхождения `provisional`, а не как способ скрыть ошибку. Невалидный shell, выход любого проёма за стену, перекрытие проёмов, стекло в непрозрачной стене и совпадающие стёкла всегда дают ошибку независимо от `confidence`.

## 7. Gate C — построение сцены

Порядок слоёв и владельцы реализации:

| Порядок | Слой | Реализация | Инвариант |
|---:|---|---|---|
| 1 | Полы, shell, стены, проходы | `buildArchitecture.js` | Стены режутся по дверям, glazing и открытым проходам. |
| 2 | Двери | `buildDoors.js` | Размер полотна и дуга связаны с одним ID. |
| 3 | Витражи | `buildGlazing.js` | Рама и стекло находятся в реальном проёме. |
| 4 | Встроенная/свободная мебель | `buildFurniture.js` | Proxy не выходит за manifest-envelope и сохраняет rotationY. |
| 5 | Светильники | `buildLights.js` | 59 visuals связаны с 13 device rigs и 22 кластерными реальными источниками; не более трёх на группу. |
| 6 | Шторы | `buildCurtains.js` | Один внутренний слой, положительный зазор до рамы/стекла. |
| 7 | Debug | `buildDebug.js` | Bounding volumes, дверные дуги, collision markers и overlay. |
| 8 | Оркестрация и камера | `SmartHomeScene.jsx` | Сцена не хранит проектные цифры вне manifest. |

После каждого геометрического слоя повторяется проверка столкновений: `architecture → openings → glazing → furniture → lighting → curtains`. Разрешённые контакты задаются адресно. Глобальное игнорирование класса столкновений и незаметное уменьшение предметов запрещены.

Collision validator использует:

- 2.5D OBB и SAT для повёрнутой мебели;
- точные составные `collisionParts` для групп и Г-образных объектов;
- вертикальное разнесение объектов;
- wall spans после вычитания дверей, проходов и glazing;
- секторные полигоны траекторий дверей;
- отдельные colliders стекла, штор и fixtures;
- явные allowed contacts с ограниченной глубиной.

Световой rig хранит `current` и `target`; изменение устройства должно плавно менять реальный свет, эмиссию fixture и пятно на полу. Curtain rig также хранит `current`/`target`; панели физически перемещаются, а не только меняют текст UI.

## 12. Оставшиеся ограничения

- Shell и большинство глобальных X/Z остаются raster-digitized `provisional` до получения векторной документации.
- Семь витражей используют разрешённые пользователем provisional `sill = 0.150 м` и `height = 3.115 м`, но не имеют подтверждённой секционности и operability.
- Вся мебель остаётся `proxy`, даже когда плановый след подтверждён.
- Материалы по цвету и физическим параметрам нуждаются в калибровке по исходным текстурам/образцам.
- Световые Y и интенсивности не заменяют светотехнический расчёт.
- Геометрия штор и ниш требует разреза или узла карниза.
- Климат — демонстрационный UI; реальных инженерных связей нет.
- Сгенерированный PNG 12,060×10,200 не может использоваться для уточнения ни одного размера.
- Любой переход от demo к реальному дому требует отдельного commissioning-манифеста и проверки безопасности.
